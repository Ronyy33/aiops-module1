## Setup

I used the cats-vs-dogs dataset from the Lecture 2 DVC demo, pulled straight from the dataset registry (the slide writes the path as `tutorial/ver/`, the actual one is `tutorials/versioning/`):

```bash
dvc get https://github.com/iterative/dataset-registry tutorials/versioning/data.zip
dvc get https://github.com/iterative/dataset-registry tutorials/versioning/new-labels.zip
```

`data.zip` unpacks to 1800 images (500 cats + 500 dogs in `train/`, 400 + 400 in `validation/`). I wrote a small script `build_index.py` that walks the extracted folder and writes `data/file_index.csv` with columns `filename, label, relpath`, sorted by path so the same input always produces a byte-identical file.

That determinism is what makes the rollback check in Part 3 actually mean something — if the md5 comes back the same, it is the exact same file, not just one with the same number of lines.

### Note on the row count

The question says v2 "should 2801". My v2 file has **2800 data rows in a 2801-line file**, since 1800 + 1000 new training images = 2800, plus one header line. I read 2801 as the line count, which matches how Part 1 describes v1 as "1800 rows + a header line" (that file is 1801 lines). Both numbers are shown in the output below so either reading can be checked.

## Part 1: Initialize DVC and push v1 to a remote

The remote is an **SSH remote**. My Ubuntu box is a UTM VM on a Mac, so the Mac host (`192.168.64.1`) acts as the remote server, with key-based auth set up via `ssh-copy-id` so DVC doesn't prompt for a password mid-transfer.

```bash
dvc init
python build_index.py data/raw          # -> 1800 rows, 1801 lines
dvc add data/file_index.csv

dvc remote add -d ssh_remote ssh://rohan@192.168.64.1/Users/rohan/dvcstore
dvc remote modify ssh_remote user rohan
dvc remote modify --local ssh_remote keyfile ~/.ssh/id_ed25519

git add -A
git commit -m "Q3: DVC init + v1 file index (1800 rows) tracked, SSH remote configured"
git tag -a v1.0 -m "data v1.0, 1800 rows"
dvc push
```

I put the keyfile in `.dvc/config.local` using `--local` on purpose, because that file is gitignored. The remote's location goes into Git so a collaborator can see it, but credentials don't.

Verifying the blob actually landed on the remote:

```bash
$ dvc push
1 file pushed

$ ssh rohan@192.168.64.1 "find ~/dvcstore -type f"
/Users/rohan/dvcstore/files/md5/33/67084a395f40c99bba930684e2d51a
```

That path is the CSV's md5 (`3367084a395f40c99bba930684e2d51a`) split into a two-character directory plus the rest — DVC stores everything content-addressed, which is why the same file can never be stored twice.

## Part 2: Simulate a data update to create v2

```bash
$ unzip -q data/new-labels.zip -d data/raw
$ find data/raw -type f | wc -l
2800

$ python build_index.py data/raw
data rows  : 2800
file lines : 2801 (rows + 1 header line)
md5        : 3cc34b3ee327c32ad25fc6f81a09bbeb

$ dvc add data/file_index.csv
$ git commit -m "Q3: v2 file index after new-labels.zip (2800 rows, was 1800)"
[main 6997d7f] Q3: v2 file index after new-labels.zip (2800 rows, was 1800)
 1 file changed, 2 insertions(+), 2 deletions(-)

$ git tag -a v2.0 -m "data v2.0, 2800 rows"
$ dvc push
1 file pushed
```

The interesting bit is `1 file changed, 2 insertions(+), 2 deletions(-)`. Git only recorded a two-line change — the old md5 out of `data/file_index.csv.dvc` and the new one in. The 2800-row CSV itself never enters Git at all; it lives in the DVC cache and on the SSH remote. That is the whole point of DVC versus committing data directly.

## Part 3: Roll back to v1 and prove the row count matches

```bash
===== BEFORE ROLLBACK (v2) =====
$ git log --oneline -1
6997d7f (HEAD -> main, tag: v2.0, origin/main) Q3: v2 file index after new-labels.zip (2800 rows, was 1800)

$ wc -l < data/file_index.csv
2801

$ md5sum data/file_index.csv
3cc34b3ee327c32ad25fc6f81a09bbeb  data/file_index.csv

===== ROLLING BACK =====
$ git checkout v1.0
Note: switching to 'v1.0'.
You are in 'detached HEAD' state. [...]
HEAD is now at f1fc5f5 Q3: DVC init + v1 file index (1800 rows) tracked, SSH remote configured

$ dvc checkout
Building workspace index |2.00 [00:00, 165entry/s]
Comparing indexes       |3.00 [00:00, 4.82kentry/s]
Applying changes        |1.00 [00:00, 169file/s]
M       data/file_index.csv

===== AFTER ROLLBACK (v1) =====
$ git log --oneline -1
f1fc5f5 (HEAD, tag: v1.0) Q3: DVC init + v1 file index (1800 rows) tracked, SSH remote configured

$ wc -l < data/file_index.csv
1801

$ md5sum data/file_index.csv
3367084a395f40c99bba930684e2d51a  data/file_index.csv
```

The line count goes 2801 → 1801, so 2800 data rows back down to 1800. More importantly the md5 comes back as `3367084a395f40c99bba930684e2d51a`, which is byte-for-byte the same hash v1 was pushed with in Part 1. Row count alone would only prove the file is the right length; the matching hash proves it is the same file.

### Why it takes two commands

`git checkout` only swaps the small `data/file_index.csv.dvc` pointer file, which contains an md5 — it does not touch the actual CSV, since Git was never tracking it. `dvc checkout` then reads that md5 and pulls the matching blob out of `.dvc/cache` (or `dvc pull` would fetch it from the SSH remote if the cache were empty) and puts it back in the workspace.

Code version and data version get restored by two separate commands pointing at the same Git commit, which is exactly the separation DVC is built around.

### Returning to the latest state afterwards

```bash
$ git checkout main
Switched to branch 'main'

$ dvc checkout
M       data/file_index.csv

$ wc -l < data/file_index.csv
2801
```
