## Part 1: Mapping (a), (b), (c) to Hidden Technical Debt Categories

### (a) Rounding logic change on "estimated delivery time" broke "favorite restaurants"

This is **Entanglement (CACE)** — *Changing Anything Changes Everything*.

The engineers only touched the rounding logic on one feature, they weren't going anywhere near favorite restaurants, but it broke anyway. That's the core of CACE: every feature weight gets optimised jointly against a single loss, so coarsening the delivery-time values shifts the loss surface and the optimiser ends up re-balancing the weights on every other feature to compensate.

Nothing in the favorite-restaurants code changed at all — the damage travelled through the shared training objective.

### (b) Marketing dashboard silently reading the raw output table

This one's **Undeclared Consumers**.

Nobody on the ML team knew marketing was pulling from that table for their campaign. So now the ML team can't change the output format or clean it up whenever they want, because there's an invisible dependency sitting there that nobody documented or agreed on.

That's the whole problem with undeclared consumers: they create hidden ties that block you from making safe changes later, and you usually only find out when something downstream breaks.

### (c) 14 undocumented shell scripts with no orchestration tool

This is **Configuration and Glue-Code Debt**.

There's no single place where the pipeline logic actually lives, it's just scattered across 14 scripts nobody documented. Hyperparameters are buried inside individual scripts with no single source of truth, execution order only exists in someone's head, and intermediate outputs aren't versioned.

It's turned into exactly the "pipeline jungle" the lecture describes, and if you want to change one hyperparameter or one step you have to dig through the whole chain to find where it's even set.

---

## Part 2: Mitigation

I'm picking **(c) Configuration and Glue-Code Debt** to fix.

The main fix is to replace the 14 shell scripts with a **DVC pipeline (`dvc.yaml`)**, which is the actual orchestration tool the setup is missing. Each stage declares its command, its dependencies, its parameters and its outputs, so the DAG stops being tribal knowledge and becomes a file in Git that anyone can read:

```yaml
stages:
  build_index:
    cmd: python scripts/build_index.py --src data/raw --out data/file_index.csv
    deps: [data/raw, scripts/build_index.py]
    outs: [data/file_index.csv]
  train:
    cmd: python train.py --lr ${train.lr} --batch-size ${train.batch_size}
    deps: [data/file_index.csv, train.py]
    params: [train.lr, train.batch_size]
    metrics: [metrics.json]
```

All the scattered hyperparameters move into one `params.yaml`, which kills the configuration half of the debt directly — one source of truth instead of 14. And `dvc repro` runs the whole chain in the right order, re-running only the stages whose inputs actually changed, so reproducing a past run doesn't depend on someone remembering the sequence.

On top of that I'd wrap the whole thing as an **MLflow Project** with an `MLproject` file declaring the entry points, parameters and environment. That way a new engineer doesn't need to know anything about the internals, they just run `mlflow run .` and every parameter that used to be buried in a script is visible and documented in one place.

Between the two, the pipeline stops being a jungle and becomes something reproducible you can actually reason about.
