### Blocker 1 — the DVC remote was unreachable

`dvc checkout` failing is expected on a fresh clone: the `.dvc` pointer file is in Git but the cache is empty, so the blob has to come from the remote first. The real problem was `dvc pull`.

The configured remote was `ssh://10.45.13.185/home/vboxuser/dvc_storage`, and Partner A's VM reported its address as `10.0.2.15` — the default VirtualBox NAT address, which every NAT'd VM has and which cannot be routed to from outside the host. NAT is outbound-only: her VM could reach the internet, but nothing could reach in.

I confirmed this was not a firewall quirk by testing both ICMP and the SSH port directly, with my own connectivity verified against `8.8.8.8`:

```bash
$ ping -c 2 10.45.13.185
2 packets transmitted, 0 received, 100% packet loss

$ nc -zv -w 3 10.45.13.185 22
nc: connect to 10.45.13.185 port 22 (tcp) timed out
```

This was resolved only after Partner A switched her VM's network adapter from NAT to **bridged**, which gave it a routable address (`10.22.85.192`), and re-pushed the updated `.dvc/config`. One local override was still needed, because the committed remote URL specifies no SSH username and would otherwise have used mine:

```bash
$ dvc remote modify --local ssh-remote user vboxuser
$ dvc pull

$ md5sum mnist_train.csv
7396020f8c1ab9425f2814ad058fa8d0  mnist_train.csv

$ ls -l mnist_train.csv
-rw-rw-r-- 1 rohan rohan 109640201 ... mnist_train.csv
```

The md5 and byte size match the values recorded in `mnist_train.csv.dvc` exactly, so the dataset I trained on is provably byte-identical to Partner A's. That is what makes the metric comparison below meaningful — without it, any difference in results could just as easily have been a difference in data.

### Blocker 2 — no `environment.yml`

Step 3 names this file specifically, and the repository does not contain it. It ships `q4/python_env.yaml` instead, which is MLflow Projects format:

```yaml

build_dependencies: [pip, setuptools]

```

`mamba env create -f` cannot parse this — it expects `name`, `channels`, and a differently structured `dependencies` block. I reconstructed an equivalent `environment.yml` from the package list above and installed those four packages into a virtualenv. **This is a deviation from the prescribed protocol and is recorded as such.**

## What the drill exposed

The metric reproduced, but **the repository was not self-sufficient**. Three gaps against the Part 1 requirements showed up only because someone else tried to run it:

1. **The data was not actually shareable.** Pushing to a DVC remote on a NAT'd VM means the push succeeds locally and the data is unreachable to everyone else. An internet-reachable remote (S3, R2) would have made this work on the first attempt, and would still work for an evaluator cloning the repository later — bridged networking only helps while both machines are on the same non-isolated network.

2. **`environment.yml` was missing.** Part 1 requires the environment to be pinned, and Part 3 names this file; `python_env.yaml` only works through `mlflow run`, not the stated protocol.

3. **No `git_commit` tag.** Part 1 lists it explicitly. Querying the run's tags returned `{}` — the script never calls `mlflow.set_tag("git_commit", ...)`, so there is no link from the logged run back to the code revision that produced it.

One further issue in `train.py` is worth recording: `parser.add_argument("--seed", type=int)` declares no default, so omitting the flag passes `None` into `train_test_split(random_state=None)` and the train/test split becomes random on every run. The forest itself is stable because `random_state=42` is hardcoded in the model, which makes the problem easy to miss — the results only diverge through the split. Running via `mlflow run` hides it too, since `MLproject` supplies `seed: 42`. Anyone running `python train.py` directly without `--seed` gets an unreproducible result from otherwise identical code and data.
